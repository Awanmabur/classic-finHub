# Classic FinHub — end-to-end product gap register (2026-11-13)

## Evidence and limits
Source: current GitHub `master` plus onboarding/email/dashboard improvements in PR #5; live MongoDB Atlas project `classic finhub` inventory and Google Search Console/PageSpeed verified in this work. Repository integration tests are *not* a substitute for a production payment/provider, authenticated browser, restoration or load test. Historical `docs/ARCHITECTURE_AND_RELEASE.md` describes an older version; prefer the current `docs/LAUNCH_STATUS.md` and live code when these documents conflict.

This is a risk-based review, not a claim that every route, CSS declaration, API, tenant permission, production provider or operating procedure has been exhaustively certified.

## P0 — must not be marketed as finished or used for unsupported real settlement

1. **Real money rails / external settlement — intentionally disabled.** `src/config/env.js` rejects `REAL_MONEY_ENABLED=true`. Ledger and reviewed manual cash/wallet/bank/forex records are *internal operations*, not proof of externally confirmed funds. Missing: scoped provider APIs, signature-verified webhooks, independently reconciled settlements, reversals/disputes, callbacks with safe idempotency/retry, compliance/KYC/AML and operations signoff. Do not fabricate a payment status.
2. **Tenant isolation credential blast radius — real production risk.** Production Atlas web principal currently has `readWriteAnyDatabase` so onboarding can provision arbitrary tenant DBs automatically. App-level tenant scoping and request authorization still matter, but compromise of the web service could access every tenant DB in the FinHub cluster. Replace long-term with a reviewed dedicated provisioning identity, per-tenant data-plane credentials, audited rotation, exact scopes and clear recovery. Do not replace with `atlasAdmin`/root.
3. **Restore evidence and operational recovery.** Encrypted host backup timer has been reported active, but live restore of an isolated tenant and full platform, PITR, offsite immutability, RPO/RTO and catastrophic recovery still require rehearsed evidence. Test a non-production restoration with real volume/config boundaries before accepting financial business data at scale.
4. **Atlas Free capacity limit.** Live Atlas inventory before this change: platform `platform_DB`: 20 collections / 53 indexes; existing tenant: 42 collections / 203 indexes. Free tier limit is 500 collections / 100 databases, 0.5 GB uncompressed storage, 38-byte DB names. With eager creation of 42 collections for each tenant, this hits collection count at approximately 11 tenants **including the existing one** (20+11×42=482, 20+12×42=524). Index storage, connection limits and throughput may be limiting earlier. Add admission/capacity monitoring; migrate to an appropriate tier and reduce eager DDL before commercial scale.

## P1 — incomplete product or production activation

5. **Invitation email sending.** Base code only displayed one-time owner/staff links. PR #5 adds Gmail send-only API support, AES-256-GCM encrypted transactional outbox, Gmail/Resend provider receipts and a clear manual fallback. Production must still configure an authorized Gmail sender, OAuth refresh token, shared invitation encryption key on web/outbox, monitor worker health, and run a real recipient smoke test. Do not call queued/accepted email delivered. For multiple workers, ensure event lease/expiry and revocation behavior is monitored; an outbox retry after provider acceptance but before recording receipt can duplicate a Gmail email, because Gmail lacks the current Resend idempotency header contract.
6. **Billing and invoicing.** `billing.service` operations, true payment collection, renewals, tax-compliant invoices, refund lifecycle and automatic settlement are not finished. `src/jobs/invoice.job.js` and `src/jobs/paymentStatus.job.js` deliberately throw. Plan publication, grants and trials are entitlement changes; never label them paid invoices.
7. **Scheduled business services.** `src/jobs/trialReminder.job.js`, `reportGeneration.job.js`, `analyticsSnapshot.job.js` are deliberately unimplemented jobs. Add schedules, distributed locks, retry/backoff, idempotency, ownership/permissions, dead letter and monitoring before enabling. Existing reports/analytics views may function independently; do not conflate those with scheduled exports.
8. **Provider SMS and Android capture.** Android Mobile Money SMS capture is separate from outbound financial PIN SMS. Twilio integration exists, Yoola/local gateway contract is still not implemented in the current runbook. Confirm sender, network permissions, handset/real device delivery, duplicate ingestion/replay resistance, and failed/uncertain provider callbacks. Notification workers currently have scoped access only to existing `classic` tenant DB; new tenants need automated least-privilege worker access or a redesigned queue boundary.
9. **Other guarded/legacy modules.** Customer portal is disabled, legacy platform users/settings and some alternate administration surfaces remain unimplemented/fail closed (see `docs/PROJECT_REVIEW.md`). Audit the *active navigation* against real database-backed handlers, not the existence of labels or disabled tabs.
10. **Tenant onboarding lifecycle.** PR #5 generates DB-safe name from the first meaningful word, auto-suffixes duplicate names, ignores browser-supplied slug, and queues invitation with tenant creation when mail transport is configured. Remaining acceptance: concurrency during simultaneous identical name/email requests, tenant creation failure after partial DDL, stale invite reissue, retries after interrupted browser response, role/branch assignment in newly created tenant, and worker authorizations.
11. **Payment/notification failure UX.** Outbox has retries, lease fencing and admin retry, but prove the real Gmail provider and SMS behavior with failed authentication, 429, 5xx, timeout, worker restart, expired invitation and wrong sender alias. Private activation links must never appear in logs or unencrypted persisted events; treat them as credentials.

## P2 — quality, visibility, maintenance and growth

12. **Platform and tenant UI consistency.** PR #5 removes manual slug entry and normalizes two dense directory tables, shared horizontal scrolling, one-line data cells and aligned action buttons while preserving existing visual theme. Full authenticated visual QA remains: 320/390/768/1024/1440 widths; staff/owner/auditor roles; every modal, form validation and empty/loading/error state; keyboard and screen reader; financial figures not clipped; mobile table scroll affordance; print and offline snapshots. Do not assert a full UI redesign is complete from CSS edits alone.
13. **SEO and AI discovery.** Live Google Lighthouse SEO for all 13 public URLs was 100 on mobile/desktop, with robots/sitemap/llms.txt available and private routes noindexed. GSC reported sitemap submitted with zero errors/warnings, 13 submitted and 0 indexed on 2026-11-13; four URLs discovered but not indexed at the time. Indexing is Google's decision; use URL Inspection/coverage, original helpful content, links and search demand. Do not target private/financial account pages for indexing.
14. **Observability and production service checks.** Verify web + outbox + notification + backup/tenant backup workers with real heartbeats, last successful job, delayed/dead letters, redacted logs, alarms to independent recipients and rollback thresholds. A healthy web HTTP response does not prove tenants can create financial records or Gmail accepted invites.
15. **Load, dependency, application security and compliance.** Validate concurrency/idempotency, index query plans, per-tenant isolation attempts, CSRF/MFA/session revocation, backup encryption and credentials, CSP, rate-limits and abuse protections, third-party pen test, SAST/DAST, privacy/retention/export/deletion and legal operating permissions for each jurisdiction. Static tests may pass while live integrations or admin permissions fail.
16. **Documentation accuracy.** Historical architecture/review documents still describe pre-financial-module functionality. Keep README, runbook, dashboard labels, plans, SEO marketing and legal pages consistent with actual manual-vs-automatic behavior. Advertise supported operations, not unimplemented payments.

## Release discipline
- Keep production DBs, existing tenant slugs, financial balances, workers and schema stable; migrate only with backups, reversible releases and a verified preflight.
- Run full CI scratch Mongo/MFA/tenant/invite/outbox flows on PR source. Then deploy only the web and matching outbox worker configuration if tests and image publication pass.
- Before enabling `MAIL_PROVIDER=gmail`, prove exact sender alias authorization and OAuth `gmail.send` scope. If not configured, preserve a secure manually shareable activation link; never claim an email was sent.
- After deployment, verify login, new tenant creation, first owner activation, staff invitation, revocation, MFA, role isolation, outbox receipt and retry, backups, SEO crawlability and existing financial reads. No payment settlement enabled.
